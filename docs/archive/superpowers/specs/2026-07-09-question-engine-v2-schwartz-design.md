# Design — Question Engine v2 + Schwartz Values Module

**Date:** 2026-07-09
**Sources:** `~/Downloads/career-question-engine-v2-build-prompt.md` (v2) + `~/Downloads/profession-values-schwartz-module.md` (Schwartz add-on)
**Status:** approved by Eugene 2026-07-09

## 0. Context and resolved conflicts

Both source documents were written against a pre-2026-07-02 repo state (they reference
`BRANCH_THEMES`, `branches`/`unlockedThemes` session fields, the `server/`+`client/` CRA
tree, and "AI-generated Big Five" as the current default — none of which exist anymore).
Decisions made with Eugene:

1. **Page 3 = hybrid.** The v2 "Oriented Field → 1st Output → Yes/No loop" replaces the
   current `direction → narrowing → professions → roadmap` question flow, BUT the
   15-direction catalog + RIASEC ranking survive as an internal grounding signal for
   output generation, and the existing roadmap generator is reused inside the Yes branch.
2. **Schwartz user vector = inference** (one AI call from already-collected data at the
   transition into `tree`, flagged low-confidence). No PVQ survey stage for now.
3. **CV input = text AND file upload** (multer + pdf-parse + mammoth).
4. **Big Five items = AI-generated by default again** (v2 §1), static IPIP is the
   fallback and the forced mode via `AI_BIG_FIVE_ITEMS=false`. The P1-1 hardened
   validator stays.

Everything ships keyless: every new AI generator gets a deterministic fallback, and the
whole flow (including non-flat Schwartz profiles) must complete without an API key.

## 1. End-to-end flow

### Page 1 — entry (App.jsx stage `entry`)
Keep the two intents (`change` | `find`) and the dream textarea. Add a second pair of
chips → `cvIntent: "new" | "use_skills"` ("Something completely new" | "Use the skills I
already have"). CV content itself is collected later, in the Page 2 `cv` step.

### Page 2 — assessment (`session.step` machine)
```
demographics → depth_choice → big_five → riasec → job_characteristics → cv → tree
```
- **demographics** — sex, age, country + **new `city` text question** (same
  validation pattern as country, max 80 chars).
- **depth_choice / big_five** — unchanged scoring. AI item generation becomes the
  default when a key is configured; static IPIP set used keyless or when
  `AI_BIG_FIVE_ITEMS=false`.
- **riasec** (NEW) — 12 items (deep: 18), 2–3 per Holland type (R,I,A,S,E,C), Likert
  1–5 "how much would you enjoy…", activity-based statements, never job titles.
  Scores = per-type mean rescaled to 0–100; `riasecCode` = top-3 letters (e.g. "IAS").
  A "skip the quiz" affordance triggers inference from Big Five + dream answer
  (AI call; deterministic fallback = Big Five–only derivation), stored with
  `riasecInferred: true` (low confidence).
- **job_characteristics** (NEW) — two sub-steps:
  1. *Rank:* order the 7 canonical parameters most→least important
     (`compensation, work_mode, job_security, career_growth, complexity,
     meaning_impact, social`). UI: tap-to-select list with ↑/↓ controls — no drag
     library.
  2. *Targeted questions:* user picks depth **5 (quick) or 10 (thorough)**; AI
     generates that many single-parameter tradeoff questions in ranking order
     (top-ranked parameters get more/first questions), 3–4 options each, every option
     encoding a 0–100 target on its parameter. Answers → `jobCharProfile`
     (0–100 per parameter; unasked parameters default to 50).
- **cv** (NEW) — if the user provides CV text (paste or file upload), one AI call
  parses it to `cvAnalysis: { skills[], domains[], seniority }`. Otherwise (either
  intent) ask the **7 static career-journey questions** (education, current/last role,
  strongest skills, liked/disliked, biggest constraint, time horizon, willingness to
  retrain) one at a time → `careerJourneyAnswers`.
  File upload: multipart via multer (memory storage), 2 MB cap, `.pdf` via pdf-parse,
  `.docx` via mammoth, `.txt` as-is; extracted text goes through the same length cap
  as the paste path.
- **Old 40-item A/B values inventory is deleted** (stage, route, scoring, question
  bank, ProfileCharts bar panel). Conceptual remap to the 7 parameters per v2 §5.4;
  no data migration needed (sessions are in-memory).

### Transition into `tree`
When the `cv` step completes, the backend computes `userValues` — the Schwartz
inference (see §4) — before advancing `step` to `tree`. The old final step name
`complete` is renamed to `tree` (frontend + CLAUDE.md updated in sync).

### Page 3 — Life Path graph (stage `tree`, `pathStage: "output" → "detail"`)
- `POST /api/output/first` generates the **Oriented Field + 1st Output**: one field,
  one concrete job, thesis, `parameterFit` explaining the job through ALL 7
  parameters against the user's targets, whyFit, firstMilestone, constraintsNote.
  Grounding: the prompt receives `rankDirections()` output (RIASEC-fit ranking over
  the 15-direction catalog) as a hint — the catalog is no longer a visible step.
- Every output is scored on Schwartz (`scoreProfessionValues`), the backend derives
  aggregates deterministically and attaches `valuesFit` vs `userValues` (§4).
- **No →** refinement panel: tick 1+ of the 7 parameters + short reason per tick, or
  "not suitable for me overall".
  - Parameter change → `POST /api/output/refine` regenerates keeping everything else
    stable but shifting the named parameters; response includes `changeSummary`.
  - Not suitable → fresh §6.3-style generation excluding the rejected field family.
  - Each regeneration appends a new `output_n` linked to its parent — the graph shows
    the iteration trail. Refine loop is not artificially capped (rate limiter is the
    backstop).
- **Yes →** `POST /api/output/accept` marks the output accepted and generates the four
  advice blocks (AI Recommendations · Events · Universities/Major · Additional
  courses, tailored to location + seniority) **and** the existing roadmap generator
  runs for the accepted job (`profession = { title: jobTitle, summary: thesis }`,
  `direction label = orientedField`), rendered with the existing roadmap node types.
- **Schwartz circle chart** (new SVG component): Openness↔Conservation ×
  Transcendence↔Enhancement plane, user point + one point per output; proximity =
  fit; each output node/dock card shows top-3 value chips + `valuesFit.overall` badge.

**Deleted from Page 3:** direction quiz (3 questions, tally, tie card),
confirm/refine/choose cycle, narrowing questions, 3-professions step — routes, UI,
session fields, and their tests. `computeDirection` and `REFINE_REASONS` die;
`DIRECTIONS` catalog + `DIRECTION_RIASEC` stay (grounding + fallbacks).

## 2. Data model (sessionStore.js)

Added:
```js
cvIntent: "new" | "use_skills" | null,
cvText: string | null,
cvAnalysis: { skills: [], domains: [], seniority: "" } | null,
riasecItems: [ { id, text, type } ],          // type serialized to client? NO — see note
riasecAnswers: { [itemId]: 1..5 },
riasecScores: { R, I, A, S, E, C } | null,     // 0..100
riasecCode: string | null,                     // e.g. "IAS"
riasecInferred: boolean,                       // true when quiz was skipped
jobCharRanking: [ 7 param keys ] | null,
jobCharDepth: 5 | 10 | null,
jobCharItems: [ { id, param, text, options: [{ value: 0..100, label }] } ],
jobCharAnswers: { [itemId]: 0..100 },
jobCharProfile: { compensation, work_mode, job_security, career_growth,
                  complexity, meaning_impact, social } | null,
careerJourneyAnswers: { [qId]: string },
userValues: { scores: {10 Schwartz keys}, confidence: "low", source: "inferred" } | null,
outputs: [ /* output objects, §3 schema */ ],
acceptedOutputId: string | null,
refinementHistory: [ { fromOutputId, changedParams: [{param, reason}],
                       notSuitable: boolean, toOutputId } ],
roadmaps: {},                                  // KEPT, re-keyed by outputId
```
Removed: `valuesAnswers`, `valuesScores`, `directionQuestions`, `directionAnswers`,
`directionTieCandidates`, `proposedDirection`, `direction`, `narrowingQuestions`,
`narrowingAnswers`, `professionOptions`, `selectedProfession`, `rejectedDirections`,
`refineNotes`. `pathStage` values become `"output" | "detail"`.

**Serialization rule (contract):** like Big Five `trait`/`reverse`, RIASEC item `type`
and jobChar option `value` ARE the scoring key — but jobChar option values are the
user-visible semantic (a target), so they may ship; RIASEC `type` must NOT ship to the
client. `serializeSessionState` static part gains `riasecItems` (id+text),
`jobCharParams` metadata, `careerJourneyQuestions`; dynamic part gains all new answer
maps/scores/outputs. `includeStatic` trimming pattern is preserved (static banks travel
on start/GET/depth/riasec-start only).

### Output object (graph payload)
```json
{
  "id": "output_1", "parentId": null,
  "orientedField": "…", "jobTitle": "…", "thesis": "…",
  "parameterFit": { "compensation": "…", "work_mode": "…", "job_security": "…",
                    "career_growth": "…", "complexity": "…", "meaning_impact": "…",
                    "social": "…" },
  "whyFit": "…", "firstMilestone": "…", "constraintsNote": "…",
  "changeSummary": "…",              // refinements only
  "schwartzValues": { "...10 keys...": 0-100 },
  "valuesRationale": { "top3 key": "one line" },
  "higherOrder": { "openness_to_change": 0-100, "self_enhancement": 0-100,
                   "conservation": 0-100, "self_transcendence": 0-100 },
  "axes": { "x_open_vs_conserv": -100..100, "y_transc_vs_enhance": -100..100 },
  "dominantPole": "…", "topValues": ["…", "…", "…"],
  "valuesFit": { "overall": 0-100, "axisFit": 0-100, "detailFit": 0-100,
                 "userPoint": {...}, "jobPoint": {...} },
  "accepted": null | true,
  "detail": null | { "aiRecommendations": [], "events": [],
                     "universities": [], "courses": [] }
}
```
The AI outputs only the 10 Schwartz scores + rationale; `higherOrder`, `axes`,
`dominantPole`, `topValues`, `valuesFit` are derived deterministically by the backend.

## 3. API surface (server.js)

Kept: `GET /api/health`, `POST /api/session/start` (**+ `cvIntent`**),
`GET /api/session/:id`, `POST /api/session/demographics`,
`POST /api/session/big-five-depth`, `POST /api/big-five/answer`.

Added:
| Route | Payload | Effect |
|---|---|---|
| `POST /api/riasec/start` | `{ sessionId }` | generate riasecItems (AI, fallback static pool), idempotent — mirrors the old `/api/direction/question` pattern so item generation never piggybacks on a cheap answer route |
| `POST /api/riasec/answer` | `{ sessionId, itemId, value 1..5 }` | record; on last item → score, derive code, advance to `job_characteristics` |
| `POST /api/riasec/skip` | `{ sessionId }` | infer scores+code (AI, fallback deterministic), `riasecInferred=true`, advance |
| `POST /api/job-characteristics/rank` | `{ sessionId, ranking[7], depth 5\|10 }` | validate permutation; generate items (AI, fallback static) |
| `POST /api/job-characteristics/answer` | `{ sessionId, itemId, value }` | value must be one of the item's option values; on last → compute profile, advance to `cv` |
| `POST /api/cv` | JSON `{ sessionId, cvText }` **or** multipart `{ sessionId, file }` | extract text, AI-parse to `cvAnalysis`; compute `userValues`; advance to `tree` |
| `POST /api/cv/journey` | `{ sessionId, questionId, value }` | record; on last of 7 → compute `userValues`; advance to `tree` |
| `POST /api/output/first` | `{ sessionId }` | generate 1st Output (idempotent: returns existing chain if present) |
| `POST /api/output/refine` | `{ sessionId, outputId, notSuitable?, changes?: [{param, reason}] }` | new linked output; records `refinementHistory` |
| `POST /api/output/accept` | `{ sessionId, outputId }` | mark accepted, `pathStage="detail"`, generate the 4 advice blocks into `output.detail` |
| `POST /api/roadmap/generate` | `{ sessionId, outputId }` (changed) | existing generator, cached in `session.roadmaps[outputId]` |

Removed: `POST /api/values/answer`, all `/api/direction/*`, all `/api/professions/*`.
All new AI-calling routes join the stricter AI rate-limit bucket. Step/stage guards:
every route 409s unless the session is at the right step (`tree`-gated for outputs),
same style as today. New backend deps: `multer`, `pdf-parse`, `mammoth`.

## 4. Schwartz module (backend/schwartzValues.js — pure, no I/O)

Implements the add-on doc §4 verbatim: `ORDER` (10 keys in circular order),
`VALUE_META` (labels + one-line meanings), `deriveHigherOrder` (hedonism split 50/50),
`deriveAxes` (x = openness − conservation, y = transcendence − enhancement),
`deriveTopValues` (top-3), `dominantPole`, `center`, `cosine`, and
`valuesFit(userV, jobV)` = `0.6 * axisFit + 0.4 * centeredCosineFit` returning
`{ overall, axisFit, detailFit, userPoint, jobPoint }`.

AI pieces (aiEngine.js):
- `inferUserValues(session)` — `buildUserValuesInferencePrompt` over Big Five, RIASEC,
  dream, jobChar ranking+profile → 10 scores, flagged low-confidence. Deterministic
  fallback: documented weight matrix from Big Five + RIASEC + jobCharProfile (e.g.
  O→self_direction/stimulation, jobChar compensation→power/achievement,
  job_security→security/conformity, meaning_impact→universalism/benevolence…).
- `scoreProfessionValues({ jobTitle, orientedField, thesis })` —
  `buildProfessionValuesProfilePrompt`; model outputs only 10 scores + top-3
  rationale, told to respect circumplex structure (opposites rarely both high, use
  the full range, flat=failure). Deterministic fallback: per-direction Schwartz
  prototype table (15 directions) modulated by the output's jobCharProfile targets —
  guaranteed non-flat.

## 5. Prompts (backend/prompts.js)

- `BASE_SYSTEM`: v2 §6.1 text **merged with** the existing anti-tech-default and
  dream-as-colour-not-filter lines (the de-bias work predates v2 and stays).
- `buildProfileDigest`: keep current core; add City, `RIASEC (0–100): R.. I.. …
  → code: XXX (measured|inferred)`, the 7 jobChar targets in ranking order, CV signal
  (skills/domains/seniority) or a career-journey summary, and the user's top Schwartz
  values once computed.
- New builders: `buildRiasecItemsPrompt(count)`, `buildRiasecInferencePrompt`,
  `buildJobCharQuestionsPrompt(ranking, count)`, `buildCvParsePrompt`,
  `buildOrientedFieldPrompt(profileDigest, directionHint)`,
  `buildRefinementPrompt(previousOutput, changes)`, `buildOutputDetailPrompt`,
  `buildUserValuesInferencePrompt`, `buildProfessionValuesProfilePrompt` — schemas per
  the two source docs (§5.3, §5.4, §6.3–6.5 of v2; §3 of Schwartz).
- Deleted: direction/narrowing/professions builders (roadmap builder stays).

Each generator in aiEngine.js follows the existing pattern: prompt → JSON mode →
strict normalizer (shape, ranges, enum checks, length caps) → deterministic fallback
on missing key/timeout/invalid payload. New static fallback banks:
`backend/riasecItems.js` (public-domain-style pool, 18+ items covering all six types)
and a static jobChar question bank (2 per parameter) in `questionPool.js`.

## 6. Frontend

- **App.jsx**: entry gains cvIntent chips; survey gains three stage UIs —
  `riasec` (Likert card, same single-click + Back pattern as Big Five, plus a
  skip link), `job_characteristics` (rank list with ↑/↓ + depth choice 5/10, then
  option-card questions), `cv` (paste textarea / file input / "ask me instead" → 7
  question cards). All keep the snapshot-is-source-of-truth pattern; local state is
  view-only indexes/drafts.
- **lifePath.js / GraphView**: graph builder reworked — `me` → output-chain nodes
  (parent-linked, refinements branch), accepted output expands into 4 advice cards +
  existing roadmap stage nodes. Dock hosts the Yes/No panel (7-parameter tick list +
  reason inputs) and the output detail.
- **New `SchwartzMap.jsx`** (custom SVG): circumplex plane with quadrant labels, user
  point + output points, fit read as proximity.
- **ProfileCharts.jsx**: values bar panel → RIASEC six-type bar panel; Big Five radar
  unchanged.
- **Progress bar**: totals recomputed (4 demo + 20/50 BF + 12/18 RIASEC + rank +
  5/10 JC + CV 1-or-7); honest time estimates updated.
- **api.js**: add wrappers for every new route (multipart helper for `/api/cv`);
  remove values/direction/professions wrappers.

## 7. Testing

- **backend (node:test + supertest):** computeRiasecScores + code derivation (incl.
  ties), jobCharProfile computation and option-value validation, every
  schwartzValues.js derivation (higher-order math, axes, centered cosine properties:
  identity→100 detailFit, opposite→0, flat-vector guard), valuesFit blend, step-order
  guards for the new machine, all new payload normalizers (malformed AI output →
  fallback), refine loop state (parent links, notSuitable path, history), CV routes
  (text, oversized file, wrong mime), keyless full-flow integration test through
  `tree` + accepted output.
- **frontend (Vitest):** graph builder over an output chain (refinement branch +
  accepted detail + roadmap), rank-list move logic, dock card selection for the new
  stages.
- Old direction/narrowing/professions tests are deleted with their code; roadmap
  tests re-keyed to `outputId`. CI must stay green both keyless and with
  `OPENAI_API_KEY` unset in CI (it already is).

## 8. Acceptance criteria (merged, hybrid-adjusted)

1. A session cannot reach the graph until demographics, Big Five, RIASEC (answered or
   explicitly skipped), job-characteristics (rank + questions), and the CV/journey
   step are complete.
2. The profile digest contains Big Five, RIASEC code (with measured/inferred flag),
   all 7 ranked parameter targets, and CV/journey signal.
3. The 1st Output explains the job through all 7 parameters.
4. "No → change parameter X" produces a new linked graph node that visibly shifts X
   while holding the rest; "No → not suitable overall" produces a genuinely different
   field.
5. "Yes" reveals the four advice blocks tailored to location + seniority AND a
   roadmap for the accepted job (existing generator).
6. Every output carries all 10 Schwartz scores (non-flat, circumplex-respecting);
   aggregates are backend-derived; `userValues` exists before the graph renders;
   every output shows `valuesFit.overall`; the Schwartz circle plots user + outputs
   with proximity matching the numeric fit; refined outputs are re-scored and
   re-plotted.
7. The whole flow completes keyless via deterministic fallbacks.
8. Existing React Flow rendering machinery (node/edge types, camera director) keeps
   working; RIASEC item `type` never ships to the client.

## 9. Delivery

Branch `feat/question-engine-v2` off `fix/audit-p0-p2`. Three phases, each leaving the
app working:
1. **Page 1–2 engine:** session shape, riasec + job_characteristics + cv steps
   (backend routes, prompts, fallbacks, frontend stage UIs), values inventory
   removal, digest update, progress bar.
2. **Schwartz core:** `schwartzValues.js`, inference + scoring generators, fit
   attachment (backend-only; exercised by tests).
3. **Page 3 output loop:** output routes + refine/accept, graph rework, refinement
   panel, advice blocks + roadmap reuse, SchwartzMap, ProfileCharts swap.
